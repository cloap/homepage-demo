## 二、技术实现

| 环节 | 方案 |
|------|------|
| 提取 | PyMuPDF 抽文字 + `find_tables` 表格**按行列还原**、独立成块 |
| 切块 | 800 字/块、重合 120 字、句末收尾；每块带「公司/章节/页码/块序号」四标签；共 **6781 块** |
| 向量 | BAAI/bge-small-zh-v1.5（512 维，本地），向量化拼入「公司名 + 章节名」 |
| 检索 | BM25（rank_bm25）+ 向量余弦，**RRF 融合**排序 |
| 回答 | DeepSeek（Anthropic 兼容 Messages API），只依据召回块作答、**关键数字带出处**，材料不足明确说「未覆盖」 |
| 页面 | Streamlit：UMAP 语义地图 + 回答 + 召回块（带页码出处） |
| 评测 | 召回与答案**分开评价**；跨公司题**逐家取证** |

## 五、结论

**同一批财报，单公司事实/指标查找题适合建库（检索式，答得准）；跨公司全景/对比题不适合建库（翻车）。**

- **答得好的（单公司）**：答案集中在「一家公司的一张表/一段」，向量（拼公司+章节）+ BM25 精确定位，表格还原后精确数值（毛利率、分红、归母净利）可抽出。
- **翻车的（跨公司）**：「谁最大/谁最快/高多少」需要先把 12 家指标**抽出、对齐口径、再排序/相减**——这是聚合，不是检索；「增速」是派生指标披露位置不一；逐家取证时关键公司（营收最大的茅台）恰恰未召回。
- **注意**：结论中的跨公司「全景失败」仅证明**本次检索实现**的局限，尚不能由此直接推断「微调更优」——两者是不同的问题形态，需方向 B 另行验证。
